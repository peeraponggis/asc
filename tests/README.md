# tests — ชุดทดสอบที่รันด้วย Node ล้วน

ไม่มี dependency ไม่ต้อง `npm install` ไม่มี build step
เหมือนกับตัวโปรแกรมที่เป็นไฟล์ static ล้วน

```bash
node tests/copilot-match.mjs
node tests/copilot-survey.mjs
node tests/copilot-holdout.mjs
node tests/batmatch.mjs
node tests/advisor-batrule.mjs
node tests/lps.mjs
node tests/lps-zone.mjs
```

ชุด `batmatch` รับพารามิเตอร์เสริมเพื่อกวาดคลังจริงทั้งคลังด้วย

```bash
node tests/batmatch.mjs --bank "F:/.../Datasheet_Extract_2026-08-31"
```

`exit 0` คือผ่าน · `exit 1` คือตก

## ทำไมมีสามชุดสำหรับเรื่องเดียวกัน

หัวใจของ ASC Copilot คือการจับคู่คำถามภาษาไทยกับหัวข้อ ซึ่งวัดผลตัวเองได้ง่ายเกินไป
ถ้าเขียนคำพ้องโดยดูชุดทดสอบเป็นตัวตั้ง ตัวเลขจะสวยโดยไม่ได้แปลว่าใช้งานจริงได้

สามชุดนี้จึงมีหน้าที่ต่างกัน และ **ตัวเลขที่เอาไปอ้างได้มีชุดเดียว**

| ไฟล์ | หน้าที่ | ผลล่าสุด | อ้างเป็นความแม่นได้ไหม |
|---|---|---|---|
| `copilot-match.mjs` | ชุดที่ใช้วัดค่าฐาน และเป็นตัวกันไม่ให้กับดักเดิมกลับมา | 15/15 | ❌ เขียนคำพ้องโดยดูชุดนี้ |
| `copilot-survey.mjs` | คำถามเรื่องเดียวกันแต่พูดคนละสำนวน | 27/28 | ❌ วัดครั้งแรกได้ 15/28 แล้วเติมคำพ้องตาม |
| `copilot-holdout.mjs` | เขียนหลังปรับคำพ้องเสร็จหมดแล้ว **ห้ามปรับคำพ้องตามชุดนี้** | **20/25 = 80 %** | ✅ **ตัวเลขนี้** |

ค่าฐานก่อนมี Copilot คือ `AscKB.search()` ตัวเดิม ซึ่งได้ **ถูก 1/15**
เพราะตัดคำด้วยช่องว่าง ซึ่งใช้กับภาษาไทยไม่ได้

### ข้อควรรู้เกี่ยวกับเลข 80 %

ชุด holdout รันครั้งแรกได้ **76 % และตอบผิด 2 ข้อ** สองข้อนั้นเป็นข้อบกพร่อง
เชิงโครงสร้าง ไม่ใช่คำพ้องขาด จึงแก้ที่ตัวตัดสิน ไม่ได้แก้ด้วยการเติมคำ
เลข 80 % หลังแก้จึงยัง **มองในแง่ดีอยู่เล็กน้อย** เพราะข้อบกพร่องถูกพบจากชุดนี้เอง

ตัวเลขจริงที่เชื่อได้ที่สุดคือบันทึกคำถามของผู้ใช้ ดูได้จากปุ่ม **สถิติ** ในแผง Copilot

## กติกาเดียวที่ห้ามละเมิด

ทั้งสามชุดยอมให้ **ตอบว่าไม่รู้** ได้ แต่ **ห้ามตอบผิด**
ผู้ใช้เชื่อคำตอบที่ผิด การเดาจึงแย่กว่าการบอกว่าไม่รู้

ทุกครั้งที่แก้ตาราง `TOPICS` ใน `docs/asc-copilot.js` ให้รันครบทั้งสามชุดก่อนเสมอ
เพราะการเติมคำพ้องหนึ่งคำอาจไปแย่งคำถามของหัวข้ออื่นโดยไม่มีอะไรเตือน

## ชุดระบบป้องกันฟ้าผ่า

`lps.mjs` ยึด **ตารางที่ 3.2 หน้า 33** ไว้ทั้งหกช่อง เพราะเป็นตารางเปิดล้วน ๆ
ลอกผิดช่องเดียวจะสั่งของผิดทั้งงานโดยที่ทุกอย่างยังดูปกติ

ก่อนงานนี้โปรแกรมใส่ SPD Type 2 ตายตัวทุกงาน ซึ่ง **ผิดในสองในสามเคส** ของตาราง
และไม่มีใครจับได้เพราะไม่มีข้อมูลระบบล่อฟ้าให้ตรวจ

ข้อที่สำคัญที่สุดในชุดนี้คือ **ข้อมูลไม่พอต้องคืน `null` ห้ามเดาเป็น class II**
ถ้าข้อนั้นตกแปลว่าถอยกลับไปเป็นพฤติกรรมเดิมที่ผิด

ชุดนี้ยังตรวจว่าไฟล์ DB2 รุ่นเก่าที่ไม่มีก้อน `lightning_protection`
ต้องไม่พัง และต้อง **เตือน ไม่ใช่ประทับตราว่าผ่าน**

`lps-zone.mjs` ตรวจการคำนวณระยะการแยก S และเขตป้องกัน

ตัวเลขในโมดูลนี้ยกมาจากเอกสารที่ **อ้างถึง** มาตรฐานของ วสท. อีกทอดหนึ่ง
ไม่ได้ยกจากตัวเล่ม การพิมพ์ผิดช่องเดียวจึงจับได้ยาก เพราะไม่มีเล่มให้เปิดเทียบ
ชุดนี้จึงยึดสองอย่างที่ **ตรวจสอบตัวเองได้**

1. **ตัวอย่างคำนวณในเอกสาร** LPS 3 · l 17 ม. -> s = 0.6 ม.
   ถ้าสูตรหรือค่าสัมประสิทธิ์ผิด ตัวอย่างจะไม่ออก
2. **ตารางมุมป้องกันต้องสอดคล้องกับเรขาคณิต** รัศมี = h x tan(α) ทั้ง 68 ช่อง
   ถ้าพิมพ์ α ผิดช่องเดียว รัศมีจะไม่ตรงกับที่เอกสารพิมพ์ไว้
   เป็นการตรวจทานข้ามที่ไม่ต้องพึ่งเล่มต้นฉบับ

และตรวจข้อที่สำคัญที่สุดของกฎ `lps-separation` คือ **ผู้ใช้ตอบขัดกับผลคำนวณ**
ต้องขึ้นเป็น `error` เพราะคำตอบนั้นไปตัดสินชนิดของ SPD ตามตารางที่ 3.2
ถ้าตอบผิดจะสั่งของผิดทั้งงานโดยที่ข้ออื่นยังเขียวหมด

**เพิ่มบทความในฐานความรู้แล้วต้องเพิ่มหัวข้อคุมด้วย** `copilot-match.mjs`
ตรวจข้อนี้ให้อยู่แล้ว ถ้าเพิ่มบทความใน `asc-kb.js` โดยไม่เพิ่มรายการใน `TOPICS`
ชุดนี้จะตกทันที เพราะบทความที่ไม่มีคำถามชี้เข้ามาคือบทความที่ผู้ใช้หาไม่เจอ

## ชุดจับคู่แบตเตอรี่กับอินเวอร์เตอร์

| ไฟล์ | หน้าที่ |
|---|---|
| `batmatch.mjs` | ตัวจับคู่ล้วน ๆ ใน `docs/asc-batmatch.js` — การแยกรายการรุ่นจากข้อความอิสระ การเทียบชื่อรุ่น และการตัดสินระดับ |
| `advisor-batrule.mjs` | กฎ `bat-inverter` และ `bat-power` ในตัวตรวจแบบ — ระดับที่ให้ ข้อความ และการไม่พังเมื่อไม่ได้โหลดโมดูล |

`batmatch.mjs` มีสองส่วน ส่วนแรกเป็นเคสที่รู้คำตอบแน่นอน **ต้องถูกทุกข้อ**
ส่วนที่สองกวาดคลังจริงทุกคู่ (อินเวอร์เตอร์ไฮบริด × แบตเตอรี่) แล้วตรวจข้อที่ยอมไม่ได้
คือ **ห้ามมีคู่ไหนถูกตัดสินว่า "ตรงตามเอกสาร" ทั้งที่ชนิดแรงดันคนละอย่าง**
เพราะถ้าเกิดขึ้นแปลว่ามีข้อมูลในคลังขัดกันเอง ต้องให้คนไปตรวจ ไม่ใช่กลบไว้
และอีกข้อคือ **ห้ามมีคู่ไหนตอบว่า "ตรงตามเอกสาร" ทั้งที่จำนวนโมดูลในตู้อยู่นอกช่วง**
เพราะรายการของผู้ผลิตเขียนเป็นชื่อตระกูล แต่ตระกูลเดียวกันมีหลายขนาดตู้
แรงดันต่างกันเกินร้อยโวลต์ เอกสารบอกว่าตระกูลนี้ใช้ด้วยกันได้
ไม่ได้บอกว่าใช้ได้ทุกขนาด ฟิสิกส์จึงต้องชนะเอกสารในข้อนี้

ผลกวาดคลังล่าสุด อินเวอร์เตอร์ไฮบริด 91 รุ่น × แบตเตอรี่ 59 รุ่น

| ระดับ | จำนวนคู่ |
|---|---|
| ตรงตามเอกสาร | 143 |
| แรงดันเข้ากันได้ | 443 |
| แรงดันล้นช่วงบางส่วน | 366 |
| ไม่เข้ากัน | 3,759 |
| ข้อมูลไม่พอ | 658 |

หลังเพิ่มแบตเตอรี่อีก 27 รุ่นในรอบถัดมา (แบต 59 -> 86 รุ่น) ตัวเลขเป็น
**doc 216 · volt 869 · partial 744 · no 5,111 · unknown 886**

ตัวเลขนี้เปลี่ยนไปจากรอบก่อน (`doc 211 · partial 971 · no 3086`) เพราะเพิ่มการคิดจำนวนโมดูล
คู่ที่ไม่มีจำนวนโมดูลไหนใช้ได้เลยย้ายจาก **ล้นช่วงบางส่วน** ไปเป็น **ไม่เข้ากัน**
และคู่ที่เอกสารระบุไว้แต่ตู้ขนาดนั้นแรงดันล้น ย้ายจาก **ตรงตามเอกสาร** ไปเป็น **ล้นช่วงบางส่วน**

`advisor-batrule.mjs` ตรวจเพิ่มอีกสองข้อที่สำคัญกว่าที่เห็น
คือ **ถ้าไม่ได้โหลด `asc-batmatch.js` กฎต้องคืน `null` เงียบ ๆ**
(หน้ารายงานรุ่นเก่าที่ยังไม่มีไฟล์นี้ต้องไม่พังทั้งแผง) และ
**จำนวนข้อตรวจเดิมต้องไม่ลดลง** เพราะกฎใหม่

กฎ `bat-power` ตรวจว่าแบตจ่ายไฟถึงพิกัดไฟสำรองของอินเวอร์เตอร์หรือไม่
ซึ่งเป็นตัวเลขที่ไปอยู่ในข้อเสนอที่ลูกค้าเซ็น ไม่ใช่เรื่องความปลอดภัย
เกณฑ์ที่ชุดทดสอบยึดไว้คือ **เตือนเฉพาะตอนจ่ายไม่ถึงพิกัดไฟสำรอง**
ส่วนการที่แบตเล็กกว่าพิกัดชาร์จสูงสุดเป็นเรื่องปกติและตั้งใจ จึงเป็นแค่ข้อสังเกต
ถ้าทำเป็นคำเตือนจะไปเตือนเกือบทุกโครงการจนคนเลิกอ่าน
