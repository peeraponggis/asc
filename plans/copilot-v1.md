## Context · ทำไปทำไม

คำตอบของคำถามที่วิศวกรถามบ่อย — *"ทำไม PR ต่ำ" · "DC/AC เท่านี้สูงไปไหม" ·
"ต้องใส่ฟิวส์กี่ตัว"* — กระจายอยู่สามที่ คือคู่มือ 242 KB · ฐานความรู้ **28 บท** ·
ผลตรวจ **36 ข้อ** ผู้ใช้ต้องเปิดหาเองทีละที่

Copilot คือชั้นที่รวมสามอย่างนี้เข้าด้วยกันแล้วตอบให้ในที่เดียว

## สิ่งที่ตัดสินใจไว้แล้ว

| เรื่อง | ที่เลือก | เหตุผล |
|---|---|---|
| ขอบเขต | **หน้าออกแบบที่เดียวก่อน** | มีข้อมูลสด · `master_shell` เห็นแค่ DB2 ที่ export แล้ว |
| LLM | **v1 ไม่ใช้เลย** | ตัดงานไปราว 40% และความเสี่ยงทั้งหมด · เสียบทีหลังได้ที่รอยต่อเดิม |
| ผู้ให้บริการ LLM (ถ้าทำ v2) | ยังไม่ตัดสิน ต้องสลับได้ | อ่านจาก secret ไม่ฝังในโค้ด |

**เกณฑ์ตัดสินว่าจะทำ v2 ไหม** ใช้ v1 จริงสักเดือน ถ้าตอบได้เกิน 80% ก็จบ ไม่ต้องมี LLM
ถ้าต่ำกว่านั้น ดูรายการคำถามที่ตอบไม่ได้ก่อนว่าเติมคำพ้องแก้ได้ไหม
ค่อยพิจารณา LLM เป็นทางสุดท้าย

## ⚠ สิ่งที่ทดสอบแล้วและเปลี่ยนขอบเขตของงาน

**`AscKB.search()` ที่มีอยู่ ใช้กับคำถามภาษาไทยไม่ได้** ทดสอบด้วยคำถามจริง 15 ข้อ

```
เจออย่างน้อย 1 บทความ  :  3/15  (20%)
ในสามข้อนั้น ตอบถูก    :  1 ข้อ   →  ความแม่นจริงราว 7%
```

ตัวอย่างที่ผิด
- *"ทำไม PR ต่ำ"* → ได้บทความ **แรงดันวงจรเปิดที่อุณหภูมิต่ำสุด** เพราะแมตช์คำว่า "ต่ำ"
- *"เบรกเกอร์ AC ขนาดเท่าไหร่"* → ได้ **อัตราส่วน DC/AC** เพราะแมตช์ "ac"

สาเหตุอยู่ที่ [`asc-kb.js:482`](../docs/asc-kb.js) ใช้ `split(/[\s,]+/)` ตัดคำด้วยช่องว่าง
แต่**ภาษาไทยไม่มีช่องว่างระหว่างคำ** พิมพ์ติดกันว่า `ทำไมค่าPRต่ำ` กลายเป็นโทเคนเดียว
หาไม่เจอเลย ส่วนคำสั้นอย่าง `ต่ำ` `ค่า` ไปโผล่ในทุกบทความจนกลายเป็นสัญญาณรบกวน

**แต่เนื้อหาไม่ใช่ปัญหา** ไล่ดูแล้ว **14 จาก 15 คำถามมีบทความรองรับอยู่แล้ว**
และ id ของบทความกับ id ของกฎตรวจแบบเกาะกันเป็นคู่อยู่แล้ว
(`pr-benchmark`↔`pr` · `dcac-ratio`↔`dcac` · `eit-string-ocpr`↔`string-ocpr`)
ทั้ง finding ก็มีฟิลด์ `kb` ชี้ไปที่บทความอยู่แล้ว

> **งานหลักของ v1 จึงคือเขียนตัวจับคู่คำถามที่ใช้กับภาษาไทยได้**
> ไม่ใช่แค่เอาตัวค้นเดิมมาต่อสาย ถ้าต่อสายเฉย ๆ จะได้ผู้ช่วยที่ตอบผิดสองในสาม
> ซึ่ง**แย่กว่าไม่มีเลย** เพราะผู้ใช้จะเชื่อคำตอบที่ผิด

## ⚠ กติกาที่ห้ามละเมิด

[`asc-advisor.js:6`](../docs/asc-advisor.js) ประกาศว่า *"ตรวจแบบด้วยกฎที่เขียนตรงๆ
**ไม่ใช้โมเดลภาษา** ... เพราะเอกสารที่ออกไปหาลูกค้ามีผลผูกพัน"*
และแผงตรวจแบบ **แสดงข้อความนี้บนหน้าจอ** ที่ `asc_design.html` บรรทัดราว 9338

> ทุกข้อคำนวณจากตัวเลขในแบบ ไม่ได้ใช้ AI

- Copilot ต้องเป็น **แผงคนละแผง** กับแผงตรวจแบบ ห้ามเอาคำตอบไปปนในรายการผลตรวจ
- **ห้ามเขียนค่าอะไรกลับเข้า `state` หรือ DB2** อ่านอย่างเดียว
- **ห้ามอยู่ในเส้นทางที่ผลิตตัวเลขในรายงาน** ลบไฟล์ Copilot ทิ้งแล้วตัวเลขทุกตัวต้องเท่าเดิม
- **ห้ามคำนวณเลขใหม่ในชั้นนี้** ทุกตัวเลขที่แสดงยกมาจาก `finding.evidence` ตรง ๆ
  อยากได้ตัวเลขใหม่ให้ไปเพิ่มกฎใน `asc-advisor.js` ซึ่งตรวจสอบย้อนกลับได้
- **ตอบว่าไม่รู้ ดีกว่าเดา**

## แนวทาง

```
asc_design.html
      │
      └─► asc-copilot.js
              │
              ├─ 1. จับคู่คำถาม → หัวข้อ   (ตัวจับคู่ใหม่ ใช้กับภาษาไทยได้)
              │
              ├─ 2. generateDB2() → AscAdvisor.analyze()
              │        หาว่าโครงการนี้มี finding ของหัวข้อนั้นไหม
              │
              ├─ 3. AscKB.get(id)  → บทความของหัวข้อนั้น
              │
              └─ 4. ประกอบคำตอบ = ผลตรวจของโครงการนี้ + บทความ + วิธีแก้จาก fix[]

ทุกอย่างทำงานในเครื่อง ไม่ต่อเน็ต ไม่ส่งข้อมูลออกนอกเครื่อง
```

**คำตอบเจาะจงโครงการที่เปิดอยู่จริง ไม่ใช่บทความกลาง ๆ** เช่นถาม *"ทำไม PR ต่ำ"*
แล้วโครงการนั้นมี finding `pr` ระดับ warn อยู่ จะได้ว่า
*"PR ของโครงการนี้อยู่ที่ 74.2% ซึ่งต่ำกว่าเกณฑ์ ... วิธีแก้ ..."* พร้อมปุ่มเปิดบทความเต็ม

### 3 · ตัวจับคู่ 3 ชั้น

1. **ตารางคำพ้อง** จับด้วย `indexOf` บนคำถามที่**ตัดช่องว่างออกแล้ว**
   จึงหาเจอทั้ง `ทำไม PR ต่ำ` และ `ทำไมค่าPRต่ำ` — ชั้นนี้เป็นตัวหลัก
2. **n-gram สำรอง** ตัดคำถามเป็นชิ้นละ 3-4 อักขระ นับว่าตรงกับชื่อบทความและแท็กกี่ชิ้น
   ใช้เป็นตาข่ายรับ ไม่ใช่ตัวหลัก
3. **ไม่เจอ → บอกว่าไม่รู้** แล้วเสนอหัวข้อใกล้เคียงให้กดเลือก **ห้ามเดา**

### 4 · ประกอบคำตอบ

```
1. finding ของหัวข้อนั้นในโครงการนี้ (ถ้ามี) → title · detail · evidence · fix[] · เลขข้อ วสท.
2. ถ้าไม่มี finding                        → บอกว่าตรวจแล้วผ่าน หรือยังไม่มีข้อมูลพอจะตรวจ
3. บทความจาก AscKB                         → ย่อหน้าแรก + ปุ่มเปิดเต็มด้วย AscKB.open()
```

## เกณฑ์ผ่าน · ต้องครบก่อนเปิด PR

**ตัวจับคู่**
1. ชุดคำถาม 15 ข้อ **ตอบถูก ≥ 13/15** และ **ห้ามมีข้อไหนตอบผิด**
2. เว้นวรรคกับไม่เว้นวรรคต้องได้ผลเดียวกัน
3. คำถามนอกขอบเขตต้องบอกว่าไม่รู้ **ห้ามเดา**
4. ชุดทดสอบเขียนไว้ในไฟล์ รันซ้ำได้

**คำตอบตรงกับโครงการที่เปิดอยู่**
5. เปิดโครงการ 724 kWp (warn 5 · info 3) ถาม *"ทำไมผลตรวจขึ้นเหลือง"* → ต้องยกทั้ง 5 ข้อจริงมา
6. ตัวเลขทุกตัวตรงกับ `finding.evidence` แบบคำต่อคำ **ไม่มีการคำนวณใหม่**
7. ยังไม่ได้วาดหลังคา กดแล้วต้องไม่ error และบอกว่ายังไม่มีข้อมูล
8. หัวข้อที่ตรวจแล้วผ่าน → ต้องบอกว่าผ่านพร้อมค่าที่วัดได้ ไม่ใช่เงียบ

**ไม่มีอะไรออกนอกเครื่อง**
9. เปิดแท็บ Network ถาม 10 คำถาม → **ต้องไม่มีคำขอออกไปข้างนอกเลยสักรายการ**

**ของเดิมไม่ขยับ**
10. แผงตรวจแบบยังเขียนว่า "ไม่ได้ใช้ AI" และคำตอบ Copilot ไม่ไปโผล่ในนั้น
11. `AscKB.search()` ไม่ถูกแก้ · ผลตรวจ 36 ข้อและตัวเลขในรายงานเท่าเดิมทุกตัว
12. ลบ `asc-copilot.js` ทิ้ง หน้าออกแบบต้องทำงานครบเหมือนเดิม

**ตัววัดผล**
13. ถาม 10 คำถามแล้วเปิดหน้าสถิติ เห็นอัตราที่ตอบได้และรายการที่ตอบไม่ได้ครบ
14. ส่งออก log ได้ไฟล์ `.json` ที่เปิดอ่านรู้เรื่อง
